How one malicious pull request helped poison AsyncAPI packages

A compromised workflow made trusted publishing part of the attack. The npm registry itself was not hijacked.

PR

Security / 2026

Written and published 10 November 2026. The date above refers to the event or measurement period, not the original publication of this article.

The incident

Microsoft Threat Intelligence identified a coordinated compromise affecting AsyncAPI packages on 14 July 2026. Five malicious versions across four npm package names were published over roughly ninety minutes.

The investigation traced the incident to a malicious pull request interacting with an unsafe GitHub Actions workflow. The configuration allowed untrusted pull-request content to execute in a privileged context.

Why this was different

The poisoned packages could run malicious code when imported into an application or build, rather than waiting for a familiar installation script. This could affect development machines, continuous-integration systems and services that used those versions.

Crucially, this was not a takeover of the entire npm registry. The attackers abused the affected project's trusted release process. Valid provenance information described a legitimate workflow even though the commits feeding it were unauthorised.

The wider takeaway

Automation is valuable because it makes releases repeatable. But automation with unnecessarily broad permissions can turn a small mistake into a distribution channel for malicious code.

Development teams should keep untrusted code away from sensitive build credentials, review workflow permissions and be ready to revoke credentials and replace compromised packages. The important question is not just which dependencies you use, but how they reach production.
